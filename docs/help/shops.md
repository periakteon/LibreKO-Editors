# Deploy merchant shops and direct-load service files

ItemSells.json, ItemExchangeExps.json, MiningExchanges.json and MiningFishingItems.json are read directly from server Seed/Data by this version. Merchant stock is not saved into a merchant database table.

1. Open the NPC/monster's Shop & loot inspector or the source document. Check SellingGroup, shop line and slot. Use Shared users before changing a group: every assigned NPC can share its stock.
2. Review the complete source document and Apply file changes. A database-only save does not deploy merchant stock. Record the changed filename and keep its file-history backup.
3. Check that all sold/reward items and referenced groups exist in the production database. Deploy associated database changes through Database configuration.
4. For every merchant stock addition, removal or slot/line move, also synchronize the matching client assets/items/items.json catalogue. Its _sell dictionary is keyed by SellingGroup as a string; each member is [ItemId, Line, Index], with exactly the same item ID, line and slot index as server ItemSells.json. Use a compatible JSON editor or your fork's catalogue tools, preserving unrelated groups and definitions. Apply file changes for ItemSells.json does not generate or update this client catalogue.
5. Rebuild and distribute the matching client using Client release, coordinated with the server deployment. The server sends only the selling-group ID when opening a shop; the client displays its local _sell list. Old clients can show removed items, miss new items or have purchases rejected after a slot move. The retail asset baker builds _sell from itemsell_table.tbl, not from the edited server ItemSells.json; rerunning that pipeline alone does not synchronize these edits.
6. Back up the deployed service files, database and complete client release. Copy the reviewed server files to the production game's actual Seed/Data directory. With the supplied Docker deployment, update the production checkout, stop game, rebuild the game image and recreate the game service; plain docker compose restart game continues using the old baked-in files.
7. Before restarting, check the database seed fingerprint/row-count rules in Database configuration. Even a shop-only image update starts the normal seeder. Do not force all seeds just to refresh a shop.
8. Start the game service and inspect the loaded merchant/service entry counts in its logs. With the updated client, open every changed line/page of each affected NPC's shop and verify names, slots, prices, currencies and item delivery; also check another NPC sharing the group. Publish the client update before allowing players to use incompatible stock layouts.
9. On failure, stop the game service, restore the coordinated prior server file/image and client catalogue release, and restart after the same seed checks. Reverse any separately saved database edits through their own guarded history. An already completed player purchase is a separate player-data operation.

For the standard image, relative Seed/Data/ItemSells.json is /app/Seed/Data/ItemSells.json. Custom bind mounts or non-container installations can have another runtime root. Confirm the root actually read by the deployed process.
