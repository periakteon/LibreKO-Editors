# Combined production release and rollback

Use this when one change crosses database, server files and client assets, such as a new item, merchant or zone. The editor reviews each destination independently and does not create a distributed transaction across them.

1. Make a release list: database/table/IDs, server relative file paths, source profile, client output version and dependencies. Decide which existing players/zones need maintenance. Confirm actual production database and process roots with the operator.
2. Take a tested production database backup and save the current server image/files and complete client release. Keep the editor's operation IDs, source hashes and client build manifest as extra evidence. Protect production credentials in your normal secret store; never paste them into release notes.
3. Rehearse on staging using a production data copy, the exact reviewed server seed/map/quest set and a clean client. Test startup seeding and row-count behavior, related records, gameplay and rollback. For custom forks, verify loader/schema/version semantics before production.
4. Save each intended editor destination and check its result. Unknown database outcomes require history reconciliation. A partial file apply leaves successful targets saved; inspect outcomes before retrying. Confirm that normal client builds use saved sources rather than an unsaved preview capture.
5. Enter maintenance and stop the affected game service. Apply reviewed database changes to the intended production database if not already there. Deploy aligned server seeds, direct-load service JSON, SMD maps and quest dependencies together. Never replace the production database with the staging database or remove its data volume as an update step.
6. Deploy the new server image/release. In the supplied Compose setup, baked files need docker compose build game followed by docker compose up -d --no-deps game after stopping the service. Plain restart does not rebuild the image. Other topologies require their own service manager and actual runtime roots.
7. Distribute the complete verified client release through the real update mechanism. Coordinate any minimum-client gate with update availability. The editor neither uploads that client nor registers it with your launcher.
8. Start the game service. Check startup seed changes, errors and affected database rows before allowing players in. Use a fresh test session to check new content, existing content, exact spawn/map points, purchases/drops, quests and event schedules. UTC and server-clock schedules use different stored clocks; verify the actual deployed timezone.
9. End maintenance only when server, database and clean/update-path client checks agree. Record the release version, actual targets, successful checks and rollback location.
10. If anything fails, keep players out. Stop the service, assess player progress since the backup and choose a targeted guarded reversal or an approved database recovery. Restore the matching prior server files/image, complete client version and version gate, then test again. Client/file rollback does not undo purchases, quest rewards or other player activity.

The supplied commands are manual operational examples, not actions the editor runs. History reversal previews current conflicts and can refuse unsafe changes; it is not a substitute for a consistent database backup and maintenance procedure.
